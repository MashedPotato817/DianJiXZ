# H 题第 3 项 · 小球定点运动（O→+5cm→-5cm）完整控制链代码审查报告

> 审查日期：2026-07-31
> 审查对象：`project/` 下实现 H 题「二、要求」第 3 项（13 分）的完整控制链
> 题目原文：*小车在静止状态时，摆杆控制装置控制小球从摆杆中心点 O 往 +5cm 处运行，到达后折返，再运行到 -5cm 处并稳定在该点附近。要求运行时间 ≤5s，±5cm 处的最大误差绝对值 ≤1cm。*
> 结论：**当前代码尚不能证明第 3 项达标**。000020 首轮实测 6205ms（超时）、过冲到 -64mm、DONE 误判；代码已修复误判的稳定判定，但 5s 总时限、±1cm 误差记录、视觉标定三大缺口仍在。

## 2. 问题清单

### 2.1 严重（直接影响第 3 项通过）

#### 问题 1 · 视觉标定未完成，系统误差直接吞掉 ±1cm 指标

- **位置**：`project/k230/ball_detect_config.py:46-57`（`IMAGE_CENTER_X=160.365`、`MM_PER_PIXEL=0.540652`、`CALIBRATION_READY=False`）；`k230_ball_detect_uart.py:361-368`（仅 `UART_ALLOW_UNCALIBRATED=True` 时发送该临时映射）
- **现象/证据**：
  - 映射来自 `-50/0/+50 mm` 三点静态拟合，残差 RMSE 0.088mm，但不含人工放置、透视、整数像素量化误差（README）；
  - 000012 实测：球在机械平衡（1780us）时 K230 报告约 -5.6mm → 视觉中心与机械中心存在系统性偏移；
  - 000020 实测：+50 处读数系统性偏低约 6mm（x≈+44 即被判为 +50）。
- **对第 3 项的影响**：±50mm 目标在 K230 坐标系偏移数 mm，叠加检测噪声（±1~2px≈±1mm）后贴近 1cm 上限；-50 侧偏移方向与量级未实测。**这是 ±1cm 指标的最大单一风险。**
- **修复建议**：
  1. 按 README 的流程完成五点标定（-50/-25/0/+25/+50，每点 3 次），用全部 15 段数据评估最大绝对误差；
  2. 用"球放 1780us 机械平衡处，记录 K230 读数"反校 `IMAGE_CENTER_X`（消除系统性偏移）；
  3. 校验通过后再置 `CALIBRATION_READY=True`。
- **验证方法**：五点重测，报告最大绝对误差与 RMSE；确认物理 ±50mm 与 K230 读数差 ≤ 数 mm。

#### 问题 2 · 5s 总时限未在代码中执行，可能"完成了但超时零分"

- **位置**：`project/mspm0/Control/ball_task.c:13`（`BALL_TASK_PHASE_TIMEOUT_MS=8000`）；`ball_task.c:85-89`（仅单段 8s 超时进 FAULT）；`ball_task.c:124`（DONE 只记 `total_ms`）
- **现象/证据**：两段各 8s，最大可到 16s 才 FAULT，与题目 5s 总时限矛盾；000020 实测 6205ms 仍输出 `POINT DONE`，无超时标记。
- **对第 3 项的影响**：现场完成但 total>5s 同样 0 分；当前代码不会阻止这种结果，也不会提示。
- **修复建议**：
  1. 增加总时限判定：`total_ms ≥ 5000` 时进 `FAULT`（或 `POINT_DONE_OVERTIME` 独立状态），使结果可判；
  2. 将 `BALL_TASK_PHASE_TIMEOUT_MS` 拆为按 5s 总预算分配（如每段 2500ms）作为前置防线；
  3. OLED/串口同时输出 `total_ms` 与是否超时。
- **验证方法**：人为让球慢速运行，确认 ≥5s 时进入 FAULT 且不再输出 DONE。

#### 问题 3 · 无"±5cm 处最大误差"记录与达标判定

- **位置**：`project/mspm0/Control/ball_task.c:112-117`（settle 只在 |error|≤5mm 且 |v|≤10mm/s 时累计 500ms）
- **现象/证据**：settle 判定是"当前采样点在容差内"，只证明判定瞬间满足条件，**不记录停留期全程最大绝对误差**；题目要求的是 ±5cm 处最大误差 ≤1cm，两者不是一回事。
- **对第 3 项的影响**：无法证明达标，评委/自查没有数据支撑。
- **修复建议**：在 `POINT_PLUS`/`POINT_MINUS` 阶段各维护 `max_abs_error`（含 valid 帧与 settle 前后窗口），DONE/FAULT 时随 `total_ms` 一并输出。
- **验证方法**：定点任务完成后，日志中出现 `POINT PLUS maxErr=…, MINUS maxErr=…`，与题目 10mm 直接比对。

#### 问题 4 · trim 静态偏差使 ±50mm 定点驻留结构脆弱（无位置积分兜底）

- **位置**：`project/mspm0/Control/ball_control.c:564-566`（输出=Kp·error+Kd·v，**无位置积分项**）；`ball_control.h:119-122`（trim 学习近关闭：KI=0.02°/mm/s、单步≤0.03°、窗口 |error|≤4mm 且 |v|≤8mm/s）
- **现象/证据**：
  - 稳态分析：球在 ±50mm 静止驻留需杆接近水平；若 trim 与真实水平角偏差 Δ（舵机角度），控制器需 `error_ss = Δ/Kp` 补偿。Kp=0.24°/mm 时：Δ=1.2°→5mm（到 settle 上限）、Δ=2.4°→10mm（=1cm 指标）、Δ=4°→16.7mm（settle 永不满足→FAULT）；
  - 文档自述：trim 曾从 122.4° 漂到 121°（1.4°）即足以让球失衡滚出画面；当前 122.4° 为人工试凑值，`BALL_CAL_ENABLE=0`（自动标定关闭）。
- **对第 3 项的影响**：±50mm 处能否保持 ±5mm（settle）完全取决于 122.4° 的手测准确性，余量仅约 1.2°；一旦机构重装/漂移，任务会以 FAULT 收场且无自动校正。
- **修复建议**：
  1. 恢复自动扫掠标定（`BALL_CAL_ENABLE=1`）或完成一次系统标定并持久化（`calib_store.c` 已具备）；
  2. 若继续信任 122.4°，在定点阶段评估启用受限位置积分（仅在 ±50mm 目标、低速时小幅积分），避免 windup；
  3. 保留 trim 学习作为慢漂兜底（当前近关闭状态对定点阶段帮助有限，需评估）。
- **验证方法**：在 ±50mm 目标静置球 5s，观察 `x_mm` 漂移量与 `trim10`；确认停留期 |error| 全程 ≤5mm。

### 2.2 中等（健壮性 / 现场可用性）

#### 问题 5 · 任务不可重入、不可复位（现场重跑需硬件复位）

- **位置**：`project/mspm0/Control/ball_task.c:46-57`（`Ball_Task_StartPoint` 仅接受 IDLE/DONE）
- **现象**：FAULT 或进行中状态无法通过按键重新触发；`control.c` 的 Key 单击已从"底盘启停"改为"启动定点任务"，无备用复位途径。
- **影响**：一次超时/失误后必须按硬件复位，现场操作不友好。
- **建议**：允许从 FAULT 重入（直接重置计时重新开始），或将双击/长按映射为"复位任务"。

#### 问题 6 · settle 计数在丢帧时冻结而非清零，可跨丢帧累计

- **位置**：`project/mspm0/Control/ball_task.c:91-94`（`position.valid==0` 时提前 return，`settle_ms` 不重置）
- **现象**：球已稳定时若链路短暂丢帧，`settle_ms` 保留原值；帧恢复后若条件仍满足则继续累计。语义上是"不连续的有效累积"，可能把 500ms 窗口拼接到丢帧两侧。
- **影响**：轻微——若球在丢帧期间漂移，恢复后的误差检查会暴露并清零；但若球确实没动，则会稍提前判定。建议显式在无效帧时清零，语义更严谨。
- **建议**：`valid==0` 时 `settle_ms=0` 并 return。

#### 问题 7 · 任务启动未校验球在 O 点

- **位置**：`project/mspm0/Control/ball_task.c:46-57`
- **现象**：`StartPoint` 不检查当前 `x_mm≈0`；球不在中心时，`total_ms` 会包含额外的归位时间，且首段向 +50 的行进距离偏长。
- **影响**：依赖操作员先手工放球到中心（README 已有说明），但无代码/显示校验，比赛紧张时易失误。
- **建议**：启动时读取 K230 位置，若 |x|>阈值（如 15mm）则拒绝启动并提示"球不在中心"。

#### 问题 8 · 链路历史误码率高，虽本轮修复有效仍需持续观察

- **位置**：`empty.c:77-78`（UART1 优先级 0 抢占 TIMER_0）；`k230_link.c:310-337`（硬件 OVRERR 计数 `rx_hw_overrun`）；`k230_link.h:12`（超时 100ms）
- **现象/证据**：
  - 早期日志（000006~000008）parse+crc 错误约 40~43%，M0 实际接受 ~7.8Hz（K230 发 ~16Hz）；文档第 15.2 节定位为 UART1 与 TIMER_0 同优先级、TIMER_0 内 400us 灰度忙等待吞字节；
  - **000020（含修复后固件）链路干净：parse_err/crc_err/timeout/rx_overrun/rx_hw_overrun 全 0**，证明该修复在该轮有效。
- **影响**：链路已不再是 000020 失败的主因；但持续丢帧会拉长 settle 的有效累计时间、压缩 5s 预算，仍需在正式测试中观察 `rx_hw_overrun` 是否保持 0。
- **建议**：正式测试前确认遥测含 25 字段（新格式），采集后检查 `parse_err+crc_err` 增速与 `rx_hw_overrun`。

### 2.3 低 / 文档

#### 问题 9 · 注释与实现不一致（按键语义）

- **位置**：`project/mspm0/Control/ball_task.h:7-9`（注释"触发：按键长按"）；`control.c:390-393`（实际**单击** `tmp==1` 触发 `Ball_Task_StartPoint`，**长按** `tmp==3` 是标定）
- **影响**：误导调试与维护。
- **建议**：`ball_task.h` 注释改为"触发：BLS 按键单击"。

#### 问题 10 · 死参数残留

- **位置**：`project/k230/ball_detect_config.py:62`（`LOG_PERIOD_FRAMES=30`）
- **现象**：`k230_ball_detect_uart.py` 已改用 `LOG_SUMMARY_PERIOD_MS`，`LOG_PERIOD_FRAMES` 未在 uart 脚本中引用（预览脚本旧参数）。

## 5. 附录 · 建议验证流程（改完后的现场测试）

1. **标定**：五点标定 → 评估最大绝对误差 → 置 `CALIBRATION_READY=True`；
2. **定点任务**：放球中心 → 单击启动 → 记录 `POINT DONE <ms>` 与各阶段 `maxErr`；重复 ≥5 次；
3. **对照**：`total_ms ≤ 5000` 且各阶段 `maxErr ≤ 10mm` 方视为该次达标；
4. **链路**：采集后检查 25 字段遥测的 `parse_err+crc_err` 增速与 `rx_hw_overrun`；
5. **过冲**：若仍出现 >10mm 过冲，单独调 `BALL_CONTROL_BRAKE_ACCEL_MM_S2` / `PASS_DAMP_*`，不要同时改多个参数。

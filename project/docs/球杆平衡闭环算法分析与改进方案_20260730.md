# 球杆平衡闭环算法分析与改进方案

> 最后更新：2026-07-31 13:00

日期：2026-07-30
状态：`ACCEL→RUN→BRAKE→CAPTURE` 混合控制、动态平衡角和短时丢帧保持已实现并通过 Keil 构建；尚待实机验证。

## 1. 背景与当前问题

当前上层小球系统由 K230 输出小球横向位置 `x_mm`，MSPM0 根据位置控制 PA8 舵机，从而改变摆杆倾角。约定如下：

- 目标位置为 `0 mm`（画面中心）；右侧为正。
- 实测：降低 PWM 会使小球向右移动、`x_mm` 增大；因此球偏右时应提高 PWM，使其向左回归。
- 舵机机械允许角度为 `5~175°`；`90°` 只作为上电初始种子，不假设它始终是物理平衡点。
- 正常快速纠偏相对动态平衡角 `trim` 限制为 `±20°`；`trim` 自身限制为 `15~165°`，给纠偏保留余量。
- 齿轮—摇杆传动比例约为：舵机转 `180°`，摆杆角度变化约 `11°`。

现象：小球在视野内（例如 `+30 mm`）可能停住，舵机虽有抖动，小球却不产生可见位移。

当前控制器为直接位置 PD：

```text
舵机偏移角 = Kp × (x - target) + Kd × d(x - target)/dt
```

当前 `Kp=0.24 °/mm`。当 `x=+30 mm` 且球静止时，输出约为 `+7.2°` 舵机偏移，折算到摆杆仅约 `0.44°`。该倾角可能不足以克服小球静摩擦、齿隙和传动阻力；同时小球静止时 D 项近似为零，控制输出不会继续积累。

## 2. 参考工程的控制算法

参考：`reference/球杆平衡控制系统/WHEELTEC_APP/RobotControl_task.c`。

参考工程采用带角度反馈的串级控制：

```text
目标小球位置
    ↓
位置 PD（50 Hz，输出目标杆角度）
    ↓
角度 P（100 Hz，输出步进频率）
    ↓
步进电机 → 摆杆
    ↑             ↑
小球位置       杆角度 ADC
```

其主要策略：

| 环节 | 参考实现 | 目的 |
|---|---|---|
| 位置外环 | `Kp=0.2`、`Ki=0`、`Kd=0.2`，50 Hz | 位置误差决定目标倾角；D 项抑制摆动 |
| D 项滤波 | 一阶低通，截止频率 2 Hz | 抑制测距噪声被微分放大 |
| 角度内环 | P 控制，100 Hz | 快速实现外环要求的摆杆角度 |
| 输出保护 | 死区、最小有效频率、最大频率 | 防止低频抖动、执行器失效和机构碰撞 |
| 调试顺序 | 传感器监视 → 方向点动 → 角度环 → 串级 | 先验证符号与执行器，再闭环 |
| 启动保护 | 传感器稳定期、PID 状态复位 | 防止启动瞬间由旧数据造成冲击 |

参考工程位置环同样刻意保持 `Ki=0`：球杆系统天然不稳定，位置积分会在球未响应时持续累积，随后容易形成过冲或振荡。

## 3. 对当前 K230 + 舵机系统的适用性

PA8 舵机内部已有位置闭环，可以近似视为参考工程的“角度内环”；但当前 MSPM0 无法读取摆杆实际角度。因此不应照搬步进频率、ADC 零点和参考 PID 数值。

可迁移的算法结构为：

```text
K230 位置帧 → 位置滤波/速度估计 → 位置 PD → 目标舵机角度
                                         ↓
                         限幅 + 静摩擦脱困 + 舵机内部位置环
```

不可直接迁移的部分：

- 参考工程的角度 ADC 内环：本系统没有摆杆角度传感器。
- 步进电机的最小频率和频率死区：舵机接口是绝对角度/PWM，不是速度指令。
- 参考工程的数值参数：执行器、机构、传感器和传动比均不同。

## 4. 建议的下一版控制策略

### 4.1 位置 PD 与受条件约束的动态平衡角

保留当前误差符号：

```text
error = x_mm - target_x_mm
servo_offset = Kp × error + Kd × velocity
```

其中 `velocity` 为滤波后的 `d(error)/dt`。球向右运动时速度为正，输出提高 PWM，有助于提前把球拉回左侧，方向与实测一致。

不加入会在所有阶段持续累积的常规位置积分。考虑到安装倾角、机构预紧和摩擦会变化，新增一个慢速动态平衡角 `trim`：

```text
servo_angle = trim + fast_correction
trim += Ki_trim × error × dt
```

`trim` 只在小球位于中心附近（`|error|≤6 mm`）、速度较低（`|v|≤12 mm/s`）且收到新有效视觉样本时更新；ACCEL、EDGE、HOLD、LOST 和 FAULT 均冻结。每帧变化不超过 `0.15°`，并限制在 `15~165°`。这不是固定的“标准 PWM”，也不是无条件积分：它只补偿缓慢变化的静态偏置。

### 4.2 为速度估计增加一阶低通

K230 的位置帧有检测噪声和不均匀到达间隔，直接差分容易使舵机高频抖动。建议将速度改为：

```text
raw_velocity = (error[k] - error[k-1]) / dt
velocity[k] = velocity[k-1] + alpha × (raw_velocity - velocity[k-1])
```

初始可将等效截止频率设在 `2~4 Hz`，之后以日志和实车响应调整。位置 PD 只在新 K230 帧到达时更新，不能在 5 ms 控制周期内对同一帧重复计算 D 项。

### 4.3 用运动确认代替固定时长 KICK

当前控制器不再“给一个脉冲后按时间回中”，而是以球的实际运动状态决定切换：

```text
ACCEL：20° → 24° → 28°连续施力，不在档位间回到 trim
  └─ 首个有效样本确认朝中心速度 ≥12 mm/s → RUN
RUN：撤掉固定同向推力，以位置/速度 PD 自然滑行
  └─ 中心外回中速度 <8 mm/s → 重新进入 ACC
  └─ 剩余误差 ≤ 估算制动距离 + 2 mm → BRAKE
BRAKE：至少 6°反向倾角进行制动
  └─ 首次过零并离开±2 mm → PASS
PASS：按起始误差20%规划3~8 mm反侧目标，只施加2~6°速度阻尼
  └─ 至少150 ms且原方向速度≤8 mm/s → 从反侧重新ACC回中
  └─ |error|≤2 mm 且 |velocity|≤8 mm/s → CAPTURE
```

ACCEL 最长 `1200 ms`；仍未确认运动则进入 `FLT` 并保持当前动态 `trim`。速度仅在新视觉帧上按实际时间差计算，并以 `alpha=0.45` 低通。上述数值均是首轮实测候选值。

### 4.4 分级限幅与安全状态

| 状态 | 建议行为 |
|---|---|
| `CAP` | 位置与速度同时进入中心容差；输出当前 `trim`，允许慢速学习平衡偏置 |
| `ACC` | 立即连续施加 `20°→24°→28°` 起动力，首个有效速度样本确认运动后退出 |
| `RUN` | 不设固定同向最小推力，使用位置/速度 PD 自然滑行，正常快速纠偏限幅 `±20°` |
| `BRK` | 根据速度平方估算制动距离，提前反向制动 |
| `PASS` | 首次过零后锁存原始方向，有限制动落到小幅反侧位置，禁止立即反向脱困 |
| `FLT` | 1200 ms 未确认运动，回到当前 `trim`，等待人工检查或复位 |
| 短时普通丢帧 | 总有效样本年龄不超过 180 ms 时保持上一安全输出和阶段 |
| 持续普通丢帧 | 回到当前 `trim` 并清空运动估计 |
| 明确左右出画面 | 保留现有边缘恢复状态机，不与常规脱困混用 |
| 机械保护 | 所有绝对角命令最终硬限在 `5~175°` |

边缘恢复的 `±75°` 不用于视野内常规控制。若 `28°` ACCEL 仍无法起球，应先核对机构、供电和方向，再决定是否扩大起动力，而不是同时提高所有状态的增益。

## 5. 实施前后的验证方法

### 5.1 先验证执行器和方向

1. 停止闭环，将舵机依次命令为 `60°、75°、90°、105°、120°`。
2. 观察摆杆实际倾角与 PWM 是否单调对应，并确认 `PWM 增加 → 小球向左加速`。
3. 记录每个角度下小球从静止开始滚动所需时间，找出最小有效舵机偏移。

### 5.2 再验证闭环

在 `x≈+30 mm` 与 `x≈-30 mm` 两侧分别静置小球，各重复至少 5 次：

| 指标 | 通过条件 |
|---|---|
| 方向 | 两侧都向中心回归，不向外侧加速 |
| 脱困 | 卡住后在设定等待时间内开始移动 |
| 收敛 | 进入中心附近后无持续大幅摆动 |
| 执行器 | 无长时间顶在限位，无异常高频抖动 |
| 视觉异常 | `LS/HD` 或帧超时不会触发持续偏转 |

### 5.3 必须记录的遥测字段

后续 K230 文本日志只能证明视觉测得的位置，不能证明 MSPM0 实际输出。因此应在 MSPM0 OLED/串口增加至少以下字段：

```text
x_mm, valid, filtered_velocity_mm_s, toward_velocity_mm_s,
stopping_distance_mm, trim_angle_deg, fast_output_deg,
control_phase, servo_pulse_us
```

这样才能区分以下三类问题：控制器给力不足、舵机/传动未响应、或小球视觉位置误判。

## 7. K230 日志数据分析与新增隐患

本节分析 `project/k230/log/` 中两份运行日志。日志仅记录 K230 应用层的终端输出，**不能证明 MSPM0 实际接收、执行了每一帧，也不能证明舵机或小球的物理响应**。

### 7.1 数据概览

| 日志文件 | 记录时长 | UART 序号范围 | 估算发送速率 | UART 有效/无效日志行 | 最长连续 UART 无效段 |
|---|---:|---:|---:|---:|---:|
| `20180101_000007_uart.txt` | 157 s | 10–2519 | 15.98 Hz | 166 / 119 | 约 27.6 s |
| `20180101_002307_uart.txt` | 842 s | 10–13499 | 16.02 Hz | 1087 / 499 | 约 66.8 s |

配置的 `SEND_PERIOD_MS=50` 对应理想发送频率约 `20 Hz`，而两份实际日志均约为 `16 Hz`。这说明完整的双通道取图、圆检测、预览显示、串口处理和文件日志共同决定了有效位置更新率。`16 Hz` 并非不能闭环，但它决定位置外环和速度估计不能按 200 Hz 的 MSPM0 定时周期来理解。

### 7.2 `vision` 与 `uart` 数值不同不等于串口错误

日志中的一行同时打印两类数据：

```text
vision: ...      # 当前循环、当前画面的检测结果
uart: ... seq=N  # 最近一次满足 SEND_PERIOD_MS 后已发送的帧
```

两者不是同一时刻采样。代码在发送周期到达时才更新 `tx_x_mm`、`tx_valid` 和 `seq`，而日志按 `LOG_PERIOD_FRAMES` 单独触发。因此测试中可见：

- 第一份日志的两者位置差最大为 `6.5 mm`；
- 第二份日志的两者位置差最大为 `9.7 mm`；
- 第二份日志中约有少量“当前视觉有效、最近 UART 帧无效”或相反的组合。

这首先是**采样时刻不同**的结果，不能据此判断 UART 丢包。不过它会误导调参：屏幕/文本上看到的当前 `vision x_mm` 并不总是 MSPM0 正在控制的值。后续应在发送分支内额外记录 `TX` 行，至少带有 `tx_x_mm`、`tx_valid`、`edge`、`seq` 和 `ticks_ms`；预览则明确标记为 `vision`，不要声称两者逐帧一致。

### 7.3 丢失持续时间远大于当前恢复时间

第二份日志有 `499` 条 UART 无效记录，其中：

- 左边缘方向 `edge=-1`：72 条；
- 右边缘方向 `edge=+1`：410 条；
- 普通丢失 `edge=0`：17 条。

也就是说，无效状态中约 `97%` 被判为“靠近画面边缘后丢失”。其中连续无效段最长约 `66.8 s`，另有约 `45.7 s`、`40.0 s` 等长段。

现有 MSPM0 边缘恢复超时为 `1 s`，超时后回中位并锁定，直到重新获得有效帧。这一策略对机构保护是正确的；但若恢复动作无法在 1 秒内把球拉回视野，系统将在长时间丢失中保持中位，无法自动恢复。日志证明这种情况至少曾出现过，因此需要在后续实测中单独记录：边缘触发时刻、恢复舵机角度、1 秒后的实际位置/帧状态和最终恢复时刻。

### 7.4 边缘方向不是物理位置的直接测量

`edge_direction` 的依据是“最后一次可靠球心是否落在图像左右各 24 px 内”，随后连续丢失达到阈值才置为 `-1/+1`。它不是小球真实到达机械端点的确认。

潜在隐患：近边缘的反光、遮挡、圆检测跳变或 ROI 截断，也可能造成同样的边缘判定。如果直接据此使用较大的恢复角度，可能在误判时施加错误的恢复动作。建议补充日志字段：`last_valid_center_x_px`、`lost_streak`、`edge_direction`、恢复状态与恢复持续时间；在未看到这些证据前，不应仅凭 `edge` 数量继续提高恢复幅度。

### 7.5 短暂漏检仍可能对 MSPM0 保持“有效”

当前配置为 `LOST_FRAMES=3`：短暂找不到圆时，K230 保留最后一次可靠 `x_mm`，在达到连续丢失阈值前仍可能发送 `valid=1`。日志中存在：

- 第一份：26 条“当前 `source=none`，但最近 UART 帧 `valid=1`”；最长可见约 `1.7 s`；
- 第二份：38 条同类记录；最长可见约 `0.6 s`。

由于日志本身异步，这些时长不能直接等同于每帧实际保持时间；但它说明控制器可能在视觉暂失时继续使用旧位置。对稳定运行这能降低瞬时抖动，对快速运动则可能形成过时控制量。速度 D 项和静摩擦脱困逻辑必须在无新有效观测时冻结或复位，不能把保持的旧位置当作连续新样本。

### 7.6 端到端链路证据不足

两份旧 K230 日志各只出现一次 `MSPM0 BALL frame acknowledged`，因为 MSPM0 只在收到首个合法 BALL 帧时回一次 ACK，并不逐帧确认。旧日志采集时使用的 ASCII 帧没有校验和，因此不能用于评价当前 CRC 链路。

当前代码已改为固定字段加 CRC-8/ATM，并由 UART0 `TELEM_V3` 输出解析错误、CRC错误、范围错误、序号缺口、接收溢出和超时。下一轮日志需记录：

```text
seq, x10, valid, edge, v10, toward_v10, stop10, trim10,
servo_us, out10, ctrl, parse_err, crc_err, range_err,
seq_gap, rx_overrun, timeout
```

旧日志只能证明曾经建链，不能替代新控制器的端到端实测。

### 7.7 标定与日志性能风险

- 两份日志都明确处于 `temporary uncalibrated UART position mode`；当前配置仍为 `CALIBRATION_READY=False`、`UART_ALLOW_UNCALIBRATED=True`。因此日志中的 `x_mm` 可用于控制方向、趋势和时序分析，不能作为实际位置精度或闭环指标。
- K230 系统时钟显示为 `2018-01-01`，仅适合分析单个文件内的相对顺序，不能与 MSPM0、手机或示波器的真实时间直接关联。
- 日志函数每次打印都会 `flush()` 文件；第二份日志还记录了 1633 次 MSPM0 心跳（约 1.94 次/s）。SD 卡写入和频繁终端输出可能引入额外帧间隔抖动，是“实际约 16 Hz”的待验证影响因素，而非已证实根因。性能测试时应提供关闭文件日志或批量刷新模式，并对比发送速率。

## 8. 基于日志的实施优先级

可观测性已经足以支持首轮控制实测，下一步不再先扩展通信功能：

1. 同时保存 K230 TX 日志和 MSPM0 `TELEM_V3`。
2. 从 `+40 mm`、`-40 mm` 各重复至少 5 次，不手动干预。
3. 先检查 `ctrl` 是否经过 `ACC→RUN→BRK→CAP`，再看 `toward_v10` 和 `stop10` 是否支持切换。
4. 若未起动，只调整 ACC；若越过中心，只调整 BRK；若中心附近慢漂，只检查 `trim10`。
5. 链路 CRC 和缺帧计数仅用于排除无效样本，不再取代球的动态调参。

## 9. 结论

当前核心问题是：控制器必须先让目标外的静止小球获得朝中心的速度，再维持滚动，并在合适位置制动；同时不能假定一个永久固定的平衡 PWM。现已实现 `ACCEL→RUN→BRAKE→CAPTURE`、条件式动态 `trim`、低通速度估计和 `5~175°` 机械保护。下一步是用 `TELEM_V3` 实测起动成功率、最大速度、制动切换点、最大超调和最终误差，再按阶段单独调参。

## 15. 2026-07-31 链路丢帧根因排查：TIMER_0与UART1中断优先级冲突

第14.2节把约40~43%的 `parse_err+crc_err` 比例归为长期背景噪声，本节排查其具体机制。硬件正处于修缮周期，本次排查限定在软件侧，不涉及接线或器件更换。

### 15.1 中断优先级冲突链条

代码检查（非实机测量，未接示波器）显示以下链条：

1. MSPM0G3507 UART硬件RX FIFO深度为4字节；115200 bps下约347 us即可填满。
2. `TIMER_0_INST_IRQHandler`（`Control/control.c`）是5 ms控制中断，`Run_Mode` 默认为1时会调用 `Gray_Mode()→Gray_Read_All()`，对8路灰度传感器逐路选通并各 `delay_us(50)`，中断服务程序内部至少400 us忙等待。
3. `empty.c` 原实现未对任何UART或TIMER中断显式设置优先级；Cortex-M0+ NVIC复位默认优先级相同，同优先级中断不能互相抢占，只能排队执行。
4. 400 us的忙等待时间超过347 us的FIFO填满时间：只要K230字节在这400 us内到达，UART1中断请求会被挂起等待，硬件FIFO在等待期间溢出，被覆盖的字节永久丢失。
5. `K230_Link_UART1_IRQHandler` 原实现只统计128字节软件ring buffer满时的 `rx_overruns`（日志中该值一直为0），未读取UART硬件 `OVRERR` 状态位，因此硬件层丢字节此前完全不可见，下游只表现为 `parse_err`/`crc_err` 上升，容易被误判为线路干扰或CRC实现问题。

`Run_Mode` 默认恒为1（`Control/control.c:34`），意味着该冲突自上电起持续存在，与是否移动线材、是否有电气干扰无关，与三组日志中误码率长期稳定在40%左右的现象吻合。此结论目前只有代码依据，尚无示波器或逐字节抓取的实机证据；下一轮实测的 `rx_hw_overrun` 计数会是直接验证。

### 15.2 本轮修改

1. `project/mspm0/empty.c`：`SYSCFG_DL_init()` 后为 `UART_1_INST_INT_IRQN` 设置优先级0（最高），`TIMER_0_INST_INT_IRQN` 设置优先级1，使UART1能抢占TIMER_0的忙等待窗口，不改动灰度巡线逻辑本身。
2. `project/mspm0/Hardware/k230_link.c`／`k230_link.h`：`K230_Link_UART1_IRQHandler` 新增对 `DL_UART_MAIN_INTERRUPT_OVERRUN_ERROR`（RIS原始状态位，不依赖中断使能、不读RXDATA数据位，避免多弹出一个字节）的检测，计入新增 `rx_hw_overruns` 诊断字段并在检测后清除该状态位；`K230_Link_Init` 同步清零并清除残留状态。
3. `project/mspm0/Control/debug_telemetry.c`：`TELEM_V3` 遥测帧末尾新增 `rx_hw_overrun` 字段，旧日志解析脚本仍可按字段数量区分旧格式（24个字段）与新格式（25个字段）。

## 17. 2026-07-31 放宽trim学习窗口，降低对手测中位值的依赖

## 18. 2026-07-31 自动扫掠标定：消除硬件更换后的基准漂移

### 18.1 问题与方案

硬件每次更换/重新安装后，舵机角度与摆杆物理倾角的映射基准都会漂移。此前靠人工试凑 `SERVO_ANGLE_NEUTRAL_DEG`（90°→98.2°→110°→122.4°，`servo.h` 注释明确"未经系统标定"），每次换硬件都要手动放球、观察、改代码、重烧。

已放宽的 `trim` 在线学习无法独立解决此问题：它只在球接近中心（|error|≤20mm）时才更新，若基准偏差过大，球根本到不了中心附近，`trim` 没有学习机会——存在"够不到中心就学不到"的死锁。

方案：利用 K230 位置反馈做**自动扫掠标定**。物理原理：摆杆不水平时球滚向较低一侧；舵机角度低于平衡角时球滚向一侧，高于平衡角时滚向另一侧。观测 K230 的 `x_mm` 滚向哪侧，二分定位"摆杆水平"的平衡角，结果写入 `trim` 初值，残余误差交给已放宽的 `trim` 在线修正。

已确认决策：按键长按触发（复用 `key.c` 的 `USEKEY_long_click`）、快速粗标定（收敛到±4~5°）、球在杆上即可。

### 18.2 实现

新增 `project/mspm0/Control/ball_calibrate.c`／`ball_calibrate.h`，状态机 `IDLE→WAIT_BALL→SETTLE→OBSERVE→DONE`，全部在5 ms控制中断内非阻塞推进：

- `WAIT_BALL`：等 K230 有效位置帧（球在杆上），3 s 内无球则放弃标定、保持原 `trim`。
- `SETTLE`（400 ms）：舵机命令到二分中点后等待球响应。
- `OBSERVE`（500 ms）：收集有效 x 样本，用前1/3与后1/3平均差判断球滚动方向；球被边缘卡住（|x|>55 mm 且趋势≈0）时按所在侧缩小上/下界。
- 收敛条件：趋势≤2 mm（球近乎静止）或迭代满8次或区间≤8°或全程超时20 s。
- `DONE`：`Ball_Control_SetTrimAngle(平衡角)` 写入 `trim` 初值，解除 `servo_hold`，闭环自动恢复。

配套改动：

- `project/mspm0/Control/ball_control.h/c`：结构体新增 `servo_hold`，`Ball_Control_Step` 开头在 `servo_hold` 时直接返回（标定期间接管舵机，防止 Reset/ApplyOutput 覆盖标定写入角度）；新增 `Ball_Control_SetServoHold` 与 `Ball_Control_SetTrimAngle` 接口。
- `project/mspm0/Control/control.c`：`Key()` 长按（`tmp==3`）触发 `Ball_Calibrate_Start()`；`TIMER_0` 中断在 `Ball_Control_Step` 前先推进标定状态机，标定激活时跳过正常闭环。
- `project/mspm0/empty.c`：初始化序列加入 `Ball_Calibrate_Init()`。
- `project/mspm0/keil/empty_LP_MSPM0G3507_nortos_keil.uvprojx`：加入 `ball_calibrate.c`。

`servo.h` 的 `SERVO_ANGLE_NEUTRAL_DEG=122.4°`（对应 PWM 1780 us）保留为无标定时的回退默认值，不再人工精调——标定结果会覆盖它。若换硬件后未标定就直接运行，行为与之前一致。

Keil 构建通过，结果为 `0 Error(s), 0 Warning(s)`；标定功能尚未做实机验证。

### 18.3 验证方法

1. 球放杆上→长按按键→观察舵机扫掠数秒后停住；遥测 `trim10` 应更新为标定结果（无论 122.4° 是否准确）。
2. 标定完成把球推到一侧，闭环应能拉回中心附近（验证 `trim` 初值有效）。
3. 无球时长按→应超时放弃，闭环保持原行为。
4. 重复标定两次结果应稳定；手动改 `servo.h` 中位值再标定应收敛到同一平衡角（验证不依赖手测初值）。

### 18.4 局限

- 标定只解决"平衡角"这一个基准。若齿轮重装后传动比也变化（180°舵机对应的摆杆角度范围不再是约11°），纠偏时每度舵角的球加速度会变，这只能靠更彻底的方案解决（例如加摆杆角度传感器做串级控制，结构参考 `reference/球杆平衡控制系统`，但需要额外硬件）。

## 19. 2026-07-31 收敛逻辑修改：PASS回程不再重新ACC，追求四分之三周期收敛

### 19.1 问题

用户目标：放球到初始偏置后，在四分之三个震荡周期内解决——起推→过零一次→回程直接停在中心，不允许反复过零。当前实测表现（`000009`/`000010`）为"过冲太大、反复过零"。

分析现有状态机，找到反复过零的直接机制：每个收敛周期的路径是 `ACC→RUN→BRAKE→PASS→重新ACC`。`Ball_Control_HandlePass` 在回程触发条件（原方向速度降到 8 mm/s 以内且至少保持 150 ms）满足时直接 `Ball_Control_StartAccel(error)`，即每过零一次就重新经历完整 `ACC→RUN→BRK→PASS` 链条。即使每次过冲衰减，也需大量周期才能收敛。

### 19.2 本轮修改

1. `project/mspm0/Control/ball_control.c`：`Ball_Control_HandlePass` 回程触发时不再 `StartAccel`，改为 `Ball_Control_ClearMotion(BALL_CONTROL_PHASE_RUN)`——转入 RUN 靠位置/速度 PD 滑回中心，由中心捕获阻尼吸住，实现单次过零收敛。若球在反侧真的停住，主循环 STALL 分支（`toward_velocity < 8 mm/s` 时重新 ACC）会脱困，不会卡死。
2. `project/mspm0/Control/ball_control.h`：`PASS_DAMP_KD_DEG_S_PER_MM` 0.05→0.07、`PASS_DAMP_HARD_MAX_DEG` 6°→8°，增强过零后阻尼，使反侧极值更小、回程更短。

中心捕获阻尼（2~8°非线性）与其它参数未动，避免破坏此前实测调好的行为。

### 19.3 预期行为与验证指标

预期收敛路径：`ACC(起推)→RUN(滑行)→BRK(中心前减速)→PASS(过零受控)→回程RUN(PD滑行)→CAP(中心捕获)`，全程只过零一次。

下一轮实测统计（从放球到稳定）：

- 过零次数：应 ≤ 1~2 次（从初始侧到反侧 1 次，若回程仍有余速可能再小幅过零，但不应进入新一轮 ACC 链条）。
- 收敛时间：从放球到 `ctrl=CAP` 并保持，应显著短于此前几十次 ACC/PASS 反复。
- `ctrl` 序列中不应再出现密集的 `ACC→RUN→BRK→PASS→ACC` 循环；PASS 之后应直接接 RUN/CAP。
- 若实测仍反复过零，下一步单独增强中心捕获阻尼（`CAPTURE_DAMP_*`），不要同时调多个参数。
